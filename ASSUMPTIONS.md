# Assumptions

Where the brief left room for interpretation, this is what I chose and why.

1. **Account ids and transaction ids are generated by the server** (UUID v4).
   Clients never supply them, which guarantees uniqueness.
2. **Money:** amounts have at most 2 decimal places (rupees and paise), must be
   greater than 0, and are stored as integer paise. Responses show them as
   numbers (for example `70.0`).
3. **Duplicate `reference_id` returns `409 Conflict`** and includes the existing
   transaction in the response, so a client that retried after a timeout can see
   what already happened. Nothing new is created and the balance is unchanged.
   The check is on `(account, reference_id)` only: a retry with a different
   amount or type is still treated as a duplicate, because the reference is
   the identity of the transaction.
4. **Insufficient balance returns `422`**, not 400 or 409, because the request is
   well formed but breaks a business rule. The balance may go to exactly 0 but
   never below.
5. **Validation failures return `422`** with a stable `code`. Unknown fields are
   rejected, which is how "the client must not set the initial balance" is enforced.
6. **`description` is optional** (defaults to an empty string). `reference_id`
   is required and may be up to 100 characters.
7. **Ordering:** "latest first" means `created_at` descending. Transactions with
   identical timestamps are ordered by insertion order.
8. **Pagination:** `page` starts at 1, `limit` defaults to 20 with a maximum of
   100. A page beyond the last one returns an empty list with a normal `200`.
9. **Transfers (bonus):** a transfer writes one debit on the source and one
   credit on the destination, both using the transfer's `reference_id` (allowed,
   since the same reference may appear on different accounts) and linked by
   a shared `transfer_id`. A transfer to the same account is rejected. A reused
   `reference_id` on either account is a duplicate.
10. **Immutability** is enforced twice: the API has no edit or delete endpoints,
    and database triggers abort any `UPDATE` or `DELETE` on transactions. Accounts
    can only change balance through transactions.
11. **No authentication, currency or account deletion**, because the brief does not
    ask for them.
12. **Database:** SQLite, chosen so the project runs with no setup. The logic
    would carry over to PostgreSQL.
